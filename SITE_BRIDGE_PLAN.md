# Site-bridge plan of record — one standard, every site conforms
2026-08-07 · v2, after the grill. Findings that motivated it: `SITE_BRIDGE_REVIEW.md`.
v1 of this plan proposed extraction only; the grill resolved the bigger question of what
lone-star IS to its sites, so the plan now covers the standard, the component kit, and
the two real sites in line to use them.

**Sam's decisions (2026-08-07), verbatim intent:**
1. **Fix the editor + bridge first. Skeen conforms to it. Then ftbk conforms to it.**
   Lone-star is never tailored to a site again — "I can't tailor it to every custom
   site. I need the sites to be built around the best lone star design strategy."
2. **The standard is prescriptive and executable** — closer to full-stack prescription:
   custom sites are built from standard editable primitives that the editor picks up
   automatically ("it can see where the text inputs, images, photos are").
3. **Keys are autogenerated, user-changeable.**
4. **Standard components are headless** — data + markers only; the site owns every
   pixel. First citizen: the standard music component (song + cover art), so new music
   keeps flowing to every site "like on Skeen's site".
5. **ftbk connects content-only in v1.** Scatter positions and folders stay site-owned.
6. **Tailwind 4 + the generated token sheet are mandatory** on every lone-star site —
   the Style panel works everywhere by construction.
7. **A template is a starter repo** — a finished SDK-built site cloned per artist. One
   editing architecture; the built-in lone-star-rendered templates become legacy.

**Definition of done (updated):** a new site built from the scaffold is editable the
moment it deploys — no manifest authored, no bridge code written — and connecting ftbk
(retrofitted to the standard) requires changes only in ftbk's repo.

---

## 1 · The industry context (unchanged from v1, abridged)

Two architectures exist: the editor owns rendering (Webflow's WFDL, Wix, Squarespace,
Bandzoogle's musician blocks) or the site owns rendering and the editor instruments it
(Storyblok's `_editable` + bridge script, Sanity's comlink + overlays + content source
maps, Builder.io's registered components). We are the second, correctly — bespoke sites
ARE the product. Every player in that camp ships the site-side contract as SDK packages
and none expects hand-mirroring; Sanity's evolution (hand attributes → helper-generated →
data-derived identity) is the maturity ladder, and decision #2 moves us up a rung:
component-generated identity. Decision #7 mirrors Storyblok/Sanity's starter templates.

## 2 · Target architecture

```
lone-star (editor, dashboard, DB)
   │  get_public_site (content)  +  postMessage bridge (editing)
   ▼
@lone-star/site-bridge        the CONTRACT: protocol, markers, style resolution,
 (framework-free core)        manifest+payload types, tokens.css, validateEditList
   ▲ imports
@lone-star/site-kit           the STANDARD PARTS (React): EditableText/Image/Video,
 (headless components)        SongCard/SongGrid, EditModeProvider, auto-key machinery,
                              DOM-derived manifest assembly (all kinds, not just text)
   ▲ starts from
create-lone-star-site         the SCAFFOLD: Next 16 + Tailwind 4 + tokens.css + /edit
 (starter repo = template)    route + kit preinstalled. A "template" is one of these,
                              finished and cloned per artist.
```

Sites in line: **skeen** (reference implementation — migrates first, deleting its ~60
hand-mirrored exports and its hand-synced `@source inline()` token list), then **ftbk**
(the desktop-OS site; the conformance stress test — nothing about it looks like skeen).

The editor keeps ONE pipeline. The "two editor styles" Sam asked about already exist in
the right form: built-in templates read lone-star's local manifests; SDK sites announce
theirs at runtime — after the kit, an announced manifest is ASSEMBLED from the standard
components rather than hand-written, which is the "automatically picked up" behavior.

## 3 · The component kit (the new heart of the plan)

**Primitives** — each stamps its own markers, contributes itself to the runtime
manifest, and is headless:

- `<EditableText k?>` — today's `<Text>`, moved to the kit. Renders stored value or
  children; stamps field + discovery attrs.
- `<EditableImage k?>` / `<EditableVideo k?>` — the missing siblings. Same contract:
  stamp identity, render stored media (or the child placeholder), report to discovery.
- `<SongGrid>` / `<SongCard>` — the standard music component. Takes the payload's
  tracks/releases, groups by `release_id` exactly as skeen's `mapMusic` does (that logic
  moves INTO the kit), stamps `item:track:<id>` per card, wires the click-shield rule
  for any embedded players. The site supplies the rendering (skeen: cover shelf; ftbk:
  desktop icons) via a render-prop/slot API.
- `<EditModeProvider>` — kills per-component `editable` prop-threading; mounts the
  bridge on `/edit`.

**Auto-keys (decision #3):** when `k` is omitted, the key derives from CONTENT — a slug
of the component's static children/label (`"COME SEE US LIVE"` → `come_see_us_live`,
collision-suffixed) — never from position, which orphans on reorder. The dev overlay
shows every generated key with a copy-to-pin affordance. The rule accepted with this
choice, stated once and loudly in the docs: **changing a component's default text
changes its auto-key and orphans that spot's saved edits** — pin keys before real
content exists on a spot.

**Discovery beyond text:** skeen's `textFieldsFromDom` generalizes into the kit — at
announce, the kit walks the DOM for its own discovery attrs and assembles the full
manifest (fields, image/video regions, components, budgets defaults). Hand-authored
edit-list entries remain possible and override discovery (skeen's slot/style declarations
keep working during migration).

## 5 · Anticipated problems

**P1. Windowed content defeats announce-time discovery.** ftbk's Music/Photos content
mounts only when its window opens — a DOM scan at announce sees an empty desktop. This
is the sharpest new problem the kit design has. Fix in the standard, not per-site: the
scaffold's `/edit` route renders with **all content surfaces mounted** (edit mode renders
windows open or hidden-but-mounted); the kit's discovery ALSO re-announces on mount of
any primitive it hasn't seen (skeen's announce-after-paint dance, generalized). Both,
because "mounted at /edit" is a rule sites can forget and re-announce is the net under it.

**P2. Auto-key orphaning** (accepted trade, decision #3). Content-derived keys move when
default copy changes. Mitigations: dev overlay lists keys + pin affordance;
`auditMarkers()` flags key collisions and key CHANGES against the last-announced set
(localStorage in dev); the dashboard's diff view already shows content rows that stopped
being read — orphans are visible, not silent.

**P3. Isomorphism.** Kit and bridge must import cleanly server-side (skeen calls
`regionProps` in server components). Framework-free core enforced by a node-env import
smoke test; DOM code confined to `frame.ts`; React confined to site-kit.

**P4. The two-repo skew window** (phases 1–2). The editor loads the DEPLOYED site;
extraction must be behavior-identical and skeen's migration goes out as one PR gated on
a preview-deploy editor session. BRIDGE_VERSION does not move for the extraction.

**P5. tokens.css is append-only forever.** Stored styles reference tokens at runtime;
sites compile CSS at build time. Removing a token orphans styling on every site at its
next build. A package test diffs against the previous published tokens.css and fails on
deletions. (This replaces skeen's hand-synced `@source inline()` list — the third mirror.)

**P6. npm release discipline.** Contract changes now require a publish; forgetting one
reintroduces drift with extra steps. CI publishes on tag; a repo check fails when
`packages/site-*` changed without a version bump. The friction is the point.

**P7. Version skew across sites is permanent.** skeen on kit 2.x, ftbk pinned to 1.x,
forever. Protocol: the ≤-version rule already covers it. Manifest: `manifestVersion`
lands in phase 4 while it's cheap; validateEditList warns (never errors in prod) on
unknown fields. Editor CI gains a compatibility fixture: last-major manifest + payload
against the current editor.

**P8. Headless components tempt style drift back in.** The first time a render-prop API
feels slow, someone ships a styled default in the kit and every site starts looking like
skeen (the Bandzoogle slide, by convenience instead of decision). Rule: the kit may ship
UNSTYLED semantic structure only; styled examples live in the scaffold, where cloning
them is a site decision.

**P9. Stryker's workspace blind spot inherits.** Both new packages join
`packages/music-rules` outside the mutation-testing net (the symlink-resolution caveat in
stryker.config.json). Contract-fixture tests are the primary guard; the exclusion is
documented where it happens.

**P10. Scope creep toward layout editing.** ftbk's scatter positions invite "can the
manager drag the icons?" — a new contract kind (site-specific layout data) the manifest
deliberately doesn't have. Held at: layout is site code. Revisit only with a concrete
artist need, as its own design.

**P11. The kit's music grouping must not fork from the dashboard's.** `mapMusic` moving
into the kit creates a THIRD copy of release-grouping unless the kit imports the same
`@lone-star/music-rules` the dashboard and DB mirror already pin. It must.

**P12. Fred's content needs the dashboard, not just the bridge.** ftbk renders profile/
works/dock — Fred's music, photos, and profile must be entered as a second artist. The
multi-artist dashboard exists, but this is the first real second tenant: expect
first-tenant assumptions (seeded skeen data, hardcoded artist references in scripts) to
surface. Budget a shakeout pass, and never run the skeen seed scripts against Fred
(they're destructive — standing rule).

## 6 · Explicitly out of scope

Unchanged from v1: no editor-owned rendering, no block editor, no stega/source-map
identity yet, no multi-artist single-deploy tenancy. Add: no layout editing (P10), no
folder curation until it's a dashboard feature (phase 7).
